# 第 18 章　打造每日工具箱：排程執行、日誌、錯誤處理與摘要

當單一範例成功後，下一個問題是每天如何可靠執行。工具箱不是把 16 支程式塞進一個巨大腳本，而是保留每支程式的單一責任，用排程器依序呼叫，再集中保存結果和錯誤摘要。

## 18.1　先畫出每日流程

一個可維護的早晨流程可以是：AI 新聞 → 書單 → 新書雷達 → 台積電行情 → 交通查詢。活動提醒另用較短間隔；Blogger 和電子書發布永遠由人工觸發。

```text
排程開始
  ├─ 查詢新聞 ─┐
  ├─ 讀取書單 ─┼─ 保存各自 outputs/ → 產生摘要
  ├─ 追蹤行情 ─┘
  └─ 發送「成功／失敗／無資料」摘要
```

每支程式有自己的輸出子目錄，失敗不應刪除其他成功結果。摘要列出程式名稱、開始／結束時間、退出碼、輸出檔案和錯誤原因。

## 18.2　用作業系統排程器

Linux 可用 cron：

```cron
0 9 * * 1-5 cd /你的專案路徑 && .venv/bin/python examples/03_data_queries/ai_news_today.py >> outputs/scheduler.log 2>&1
```

Windows 使用工作排程器，動作指定 `.venv\Scripts\python.exe`，引數指定範例完整路徑，起始位置指定專案根目錄。macOS 可使用 launchd 或先用 Terminal 手動驗證。排程設定本身不要寫入包含個人路徑的公開範例，書籍只提供格式和檢查方式。

## 18.3　日誌和退出碼

不要只依賴 `print`。每次執行記錄結構化欄位：`started_at`、`finished_at`、`status`、`output`、`error`。成功但無資料是 `status=ok_empty`；網路中斷是 `status=error`；資料不完整是 `status=invalid`。退出碼讓排程器知道是否需要通知。

集中工具可以用 `subprocess.run(..., capture_output=True, text=True)` 呼叫既有程式，保存 stdout 和 stderr，再以 `returncode` 判斷結果。不要吞掉 stderr，也不要因一支程式失敗就刪除整天的輸出。

## 18.4　重試和節流

網路短暫失敗可以有限次重試，每次增加等待時間；選擇器改版不應無限重試。不同網站之間保留合理間隔，不要同時大量請求。行情和新聞來源有自己的限制，遵守服務條款並保存來源時間。

## 18.5　每日摘要

摘要可以是 Markdown：新聞幾則、新書幾本、行情是否有效、交通查詢是否成功、活動狀態是否改變。摘要連結到各自的 JSON、CSV、HTML 報告，而不是把所有原始資料塞進一個檔案。這讓人先讀重點，需要時再追查細節。

## 18.6　練習

1. 先手動依序執行三支唯讀範例，為每支記錄開始時間、退出碼和輸出檔案。
2. 寫一個小型 runner，只呼叫 E06、E12 和 E10，遇到失敗繼續下一支並最後列出失敗清單。
3. 為 runner 加入 `--dry-run`，只列印將執行的命令，不真正連線。

至此，你已從安裝、單頁操作、資料查詢、狀態追蹤走到排程設計。真正可靠的自動化不是永遠成功，而是成功、空結果和失敗都能被看見、被解釋、被再次檢查。
